# IMPLEMENTAÇÃO DE MULTI-TENANCY - MARCWEB

## Visão Geral

Este documento descreve a arquitetura e os detalhes da implementação do sistema de **multi-tenancy** no MarcWeb, permitindo que diversas empresas utilizem a mesma API e o mesmo banco de dados PostgreSQL, com isolamento completo dos dados por meio de **schemas separados**.

---

## 1. CONCEITO ESCOLHIDO

### 1.1 Estratégia: Shared Database, Separate Schemas

O sistema utilizará uma única base de dados (database) com múltiplos schemas:

- **Schema `public`**: Armazena dados globais compartilhados entre todas as empresas (tabelas de Tenants e Usuários)
- **Schemas `tenant_{identificador}`**: Cada empresa terá seu próprio schema isolado contendo todos os dados operacionais

## 2. REGRAS DE NEGÓCIO DEFINIDAS

### 2.1 Isolamento de Usuários

- Cada usuário pertence a um único tenant
- O user_id 1 do tenant "empresa001" é completamente diferente do user_id 1 do tenant "empresa002"
- Mesmo que seja a mesma pessoa física, serão registros diferentes

### 2.2 Unicidade de Dados

- **Username**: Pode se repetir em diferentes tenants (mesmo username "admin" pode existir em múltiplas empresas)
- **CNPJ**: Único por tenant (não pode ter duas empresas com mesmo CNPJ)
- **Email/Dominio**: Único por tenant

### 2.3 Criação de Schemas

- Os schemas serão criados automaticamente pela aplicação
- No primeiro acesso de um novo tenant, o sistema criará o schema correspondente
- As tabelas serão geradas automaticamente dentro do schema do tenant

## 3. ESTRUTURA DE DADOS

### 3.1 Tabelas no Schema Public

#### Tabela: tenants

Responsável por armazenar o cadastro de todas as empresas que utilizam o sistema.

| Campo | Tipo | Descrição |
|-------|------|-----------|
| id | BIGINT | Identificador interno (auto-incremento) |
| tenant_id | VARCHAR(50) | Identificador único da empresa (ex: "empresa001") |
| nome | VARCHAR(200) | Razão social da empresa |
| cnpj | VARCHAR(18) | CNPJ da empresa (único) |
| dominio | VARCHAR(100) | Domínio para futura integração web |
| ativo | BOOLEAN | Se a empresa está ativa no sistema |
| created_at | TIMESTAMP | Data de criação do registro |
| updated_at | TIMESTAMP | Data da última atualização |

#### Tabela: users

Agora com referência ao tenant, permitindo usuários com mesmo username em tenants diferentes.

| Campo | Tipo | Descrição |
|-------|------|-----------|
| id | BIGINT | Identificador interno |
| tenant_id | VARCHAR(50) | Referência ao tenant (FK) |
| nome | VARCHAR(150) | Nome completo do usuário |
| username | VARCHAR(100) | Nome de usuário (único por tenant) |
| password | VARCHAR(255) | Senha criptografada |
| role | VARCHAR(20) | Função (ADMIN, EMPLOYEE) |
| ativo | BOOLEAN | Se o usuário está ativo |
| consent_geoloc | BOOLEAN | Consentimento de geolocalização |
| cargo | VARCHAR(100) | Cargo do funcionário |
| cpf | VARCHAR(14) | CPF do funcionário |
| created_at | TIMESTAMP | Data de criação |

**Restrição Unique**: A combinação (tenant_id + username) deve ser única, garantindo que o mesmo username possa existir em tenants diferentes.

### 3.2 Tabelas por Schema de Tenant

Cada tenant terá em seu schema as seguintes tabelas:

#### Tabelas Operacionais

- **configs_empresa**: Configurações específicas da empresa (localização, raio de geolocalização)
- **registros_ponto**: Todos os registros de ponto dos funcionários
- **feriados**: Feriados da empresa
- **folgas**: Solicitações de folga dos funcionários
- **folhas_ponto**: Resumos mensais de ponto
- **logs_auditoria**: Registros de auditoria das operações

## 4. ARQUITETURA TÉCNICA

### 4.1 Componentes Backend

#### TenantContext

Componente responsável por armazenar o tenant atual durante o processamento de cada requisição HTTP.

- Utiliza ThreadLocal para manter o tenantId disponível durante toda a requisição
- Permite que qualquer parte do código acesso o tenant atual
- É limpo após o processamento de cada requisição

#### TenantSchemaResolver

Componente que integra com o Hibernate para determinar qual schema deve ser utilizado em cada operação de banco de dados.

- Implementa a interface CurrentTenantIdentifierResolver do Hibernate
- Retorna o nome do schema baseado no TenantContext
- Schema retornado no formato "tenant_{tenantId}"

#### TenantDataSource

Provider de conexões com o banco de dados que configura automaticamente o schema correto em cada conexão.

- Implementa MultiTenantConnectionProvider do Hibernate
- Configura o schema da conexão antes de retorná-la
- Após o uso, restaura a conexão ao schema padrão

#### TenantFilter

Filtro de requisições HTTP que extrai o tenantId do token JWT e configura o TenantContext.

- Intercepta todas as requisições autenticadas
- Extrai o tenantId do payload do JWT
- Configura o TenantContext para uso durante a requisição

#### TenantSchemaService

Serviço responsável por criar os schemas de tenant automaticamente.

- Verifica se o schema já existe antes de criar
- Cria todas as tabelas necessárias no schema do tenant
- Cria os índices para otimização de consultas
- É chamado na primeira vez que um tenant acessa o sistema

### 4.2 Fluxo de Dados

```
┌──────────────────────────────────────────────────────────────────┐
│                    FLUXO DE UMA REQUISIÇÃO                        │
└──────────────────────────────────────────────────────────────────┘

1. USUÁRIO ENVIA REQUISIÇÃO
   │
   ▼
2. TENTANT FILTER INTERCEPTA
   │   └── Lê o token JWT do header Authorization
   ▼
3. EXTRAI TENANTID DO TOKEN
   │   └── O tenantId está embedded no payload do JWT
   ▼
4. CONFIGURA TENANTCONTEXT
   │   └── Armazena o tenantId no ThreadLocal
   ▼
5. HIBERNATE SOLICITA CONEXÃO
   │   └── Através do TenantDataSource
   ▼
6. DATASOURCE CONFIGURA SCHEMA
   │   └── Executa SET SCHEMA = 'tenant_{tenantId}'
   ▼
7. OPERAÇÃO JPA EXECUTADA
   │   └── Query executa no schema correto do tenant
   ▼
8. CONEXÃO RETORNA AO SCHEMA PÚBLICO
   │   └── TenantContext é limpo
   ▼
9. RESPOSTA RETORNA AO CLIENTE
```

### 4.3 Integração com JWT

O token JWT será modificado para incluir o tenantId:

**Payload do Token Atual:**
```json
{
  "sub": "admin",
  "role": "ADMIN",
  "exp": 1234567890
}
```

**Payload do Token com Tenant:**
```json
{
  "sub": "admin",
  "role": "ADMIN",
  "tenantId": "empresa001",
  "exp": 1234567890
}
```

O JwtService será responsável por:
- Incluir o tenantId no token no momento do login
- Extrair o tenantId do token em cada requisição

## 5. INTEGRAÇÃO COM FRONTEND

### 5.1 Fluxo de Login

O frontend já possui um dropdown de seleção de empresa no formulário de login. O fluxo será:

1. **Usuário acessa a página de login**
2. **Seleciona a empresa no dropdown** (já existe no HTML)
3. **Preenche usuário e senha**
4. **Frontend envia**: username, password E tenantId selecionado
5. **Backend valida** o usuário no schema public, buscando pelo tenantId específico
6. **Backend gera JWT** com o tenantId no payload
7. **Frontend armazena** o token e o tenantId no localStorage
8. **Requisições futuras** incluem o header X-Tenant-Id

### 5.2 Dados Armazenados no Frontend

```json
{
  "id": 1,
  "username": "admin",
  "role": "ADMIN",
  "token": "eyJ...",
  "tenantId": "empresa001"
}
```

### 5.3 Header em Todas Requisições

Todas as chamadas à API incluirão:
- Header `Authorization`: Bearer {token}
- Header `X-Tenant-Id`: {tenantId} (para redundância e validação)

## 6. IMPLEMENTAÇÃO PROGRESSIVA

### Fase 1: Estrutura Base

1. Criar a Entity Tenant
2. Criar TenantContext e TenantFilter
3. Configurar TenantSchemaResolver e TenantDataSource
4. Criar TenantRepository

**Resultado**: Estrutura de contexto e filtros prontos

### Fase 2: Banco de Dados

1. Criar tabela de tenants
2. Adicionar coluna tenantId na tabela users
3. Criar constraint de unicidade por tenant+username

**Resultado**: Banco de dados pronto para multi-tenancy

### Fase 3: Lógica de Schemas

1. Implementar TenantSchemaService
2. Configurar criação automática de schemas
3. Modificar TenantDataSource para criar schemas sob demanda

**Resultado**: Schemas criados automaticamente

### Fase 4: Integração JWT

1. Modificar JwtService para incluir tenantId
2. Modificar JwtAuthenticationFilter para extrair tenantId
3. Atualizar LoginRequest e LoginResponse

**Resultado**: Login retorna e armazena tenantId

### Fase 5: Frontend

1. Modificar script_login.js para enviar tenantId
2. Armazenar tenantId no localStorage
3. Adicionar header X-Tenant-Id em todas requisições

**Resultado**: Integração completa com interface

### Fase 6: Validação

1. Testar criação de múltiplos tenants
2. Validar isolamento de dados
3. Testar login com diferentes empresas

**Resultado**: Sistema pronto para produção

## 7. SEGURANÇA

### 7.1 Isolamento de Dados

- O tenantId é extraído exclusivamente do JWT, que é assinado digitalmente
- O frontend não pode manipular o tenantId diretamente
- O filtro de segurança valida que o usuário só acessa dados do seu tenant

### 7.2 Validação de Acesso

A cada operação, o sistema garante que:
- O usuário está autenticado (token válido)
- O token contém o tenantId
- As operações só afetam dados do tenant do usuário

### 7.3 Proteção contra Queries Cruzadas

Graças ao isolamento por schema:
- Não é possível acidentalmente consultar dados de outro tenant
- Cada conexão está configurada com o schema correto
- O Hibernate gera queries sempre no schema do tenant atual

## 8. BENEFÍCIOS DA ARQUITETURA

### 8.1 Isolamento Completo

- Cada empresa tem seus dados completamente isolados
- Não há risco de vazamento de dados entre empresas
--backup e restore podem ser feitos por tenant

### 8.2 Flexibilidade

- Cada tenant pode ter suas próprias configurações
- Possível migrar um tenant para outro servidor no futuro
- Escala independentemente do tamanho de cada empresa

### 8.3 Manutenção Simplificada

- Uma única aplicação para todos os tenants
- Atualizações rodadas uma vez funcionam para todos
- Monitoramento centralizado

### 8.4 Performance

- Queries não precisam filtrar por tenantId (schema já Isola)
- Índices específicos por tenant
- Conexões otimizadas por schema

---

## 9. CENÁRIOS DE USO

### 9.1 Primeira vez que uma empresa acessa

1. Usuário tenta fazer login com empresa nova
2. Sistema verifica que o tenant existe
3. Sistema cria o schema automaticamente
4. Sistema cria todas as tabelas no schema
5. Login é processado normalmente

### 9.2 Usuário comum acessa

1. Usuário seleciona sua empresa no dropdown
2. Preenche credenciais
3. Backend valida usuário no schema public
4. Backend gera token com tenantId
5. Todas operações usam o schema do tenant

### 9.3 Admin cria novo usuário

1. Admin está logado em um tenant
2. Acessa tela de cadastro de usuários
3. Sistema cria usuário no schema public com o tenantId do admin
4. Novo usuário pode acessar normalmente

## 10. CONSIDERAÇÕES ADICIONAIS

### 10.1 Migrações de Dados Existentes

Ao implementar esta arquitetura em produção:
- Criar o tenant "legacy" para dados existentes
- Todos os usuários atuais receberão este tenantId
- O sistema continuará funcionando normalmente

### 10.2 Future Features

- **Domínio próprio**: Cada tenant pode ter seu próprio subdomínio
- **Dashboard por tenant**: Relatórios específicos por empresa
- **Configurações por tenant**: Personalização da interface

### 10.3 Monitoramento

- Logs devem incluir o tenantId para rastreabilidade
- Métricas de uso por tenant
- Alertas de uso anormal por empresa
