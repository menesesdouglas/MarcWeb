## 🔴 BUGS CRÍTICOS (PRIORIDADE MÁXIMA)

### BUG-001: Primeiro Registro Não Validava Tipo ENTRADA
**Status**: ✅ CORRIGIDO

**Localização**: `src/main/java/com/marcweb/service/RegistroPontoService.java`

**Descrição**: 
O sistema não validava se o primeiro registro de ponto de um usuário era do tipo ENTRADA. Usuários podiam iniciar com INICIO_DESCANSO, FIM_DESCANSO ou SAIDA, quebrando a lógica de negócio.

**Impacto**:
- Quebra de regras de negócio
- Dados inconsistentes no banco
- Impossibilidade de calcular horas trabalhadas corretamente

**Comportamento Esperado**:
O primeiro registro de ponto de qualquer usuário DEVE ser obrigatoriamente do tipo ENTRADA.

**Correção Implementada**:
Adicionada validação específica para verificar se o último registro é null (primeiro registro do usuário) e garantir que o tipo seja ENTRADA.

---

### BUG-003: Validação de Geolocalização NÃO Implementada
**Status**: ✅ CORRIGIDO

**Localização**: `src/main/java/com/marcweb/service/RegistroPontoService.java`

**Descrição**:
O sistema não valida se o registro de ponto está sendo feito dentro do raio permitido da empresa quando a geolocalização está ativa. O código aceita qualquer coordenada GPS sem verificação.

**Impacto**:
- CRÍTICO para segurança
- Funcionários podem registrar ponto de qualquer localização
- Invalida o propósito da funcionalidade de geolocalização
- Não respeita configurações de `geolocAtiva` e `raioGeoloc`

**Comportamento Atual**:
Sistema aceita latitude/longitude sem nenhuma validação de distância.

**Comportamento Esperado**:
1. Se `ConfigEmpresa.geolocAtiva = true`, validar presença de coordenadas
2. Calcular distância usando fórmula de Haversine
3. Rejeitar registro se distância > `ConfigEmpresa.raioGeoloc`
4. Lançar exceção apropriada com distância calculada

**Correção Implementada**:
Adicionada validação específica para verificar se a localização do usuário está dentro do perímetro exigido pela empresa.

---

### BUG-004: Validação de Dia Útil NÃO Implementada
**Status**: ✅ CORRIGIDO

**Localização**: `src/main/java/com/marcweb/service/RegistroPontoService.java`

**Descrição**:
Sistema permite registro de ponto aos domingos e em feriados, contrariando a regra de negócio que estabelece bloqueio automático destes dias.

**Impacto**:
- CRÍTICO para regras trabalhistas
- Permite horas extras indevidas
- Gera inconsistências na folha de ponto
- Viola conformidade legal (CLT)

**Comportamento Atual**:
Sistema aceita registro em qualquer dia da semana, incluindo domingos e feriados cadastrados.

**Comportamento Esperado**:
1. Bloquear registro aos domingos automaticamente
2. Bloquear registro em feriados cadastrados no banco
3. Retornar mensagem clara informando o motivo da rejeição

**Correção Implementada**:
Adicionada validação para feriados e domingos.

## 🟡 BUGS ALTA PRIORIDADE

### BUG-005: Query JPQL com Enum Incorreta
**Status**: ❌ PENDENTE

**Localização**: `src/main/java/com/marcweb/repository/FeriadoRepository.java`

**Descrição**:
A query JPQL que busca feriados manuais sem ID está usando a referência do enum de forma incorreta, causando erro em tempo de execução.

**Código Problemático**:
```
@Query("Select new Feriado(...) from Feriado f where f.origem = MANUAL ...")
```

**Impacto**:
- Método `atualizarFeriados()` falha ao executar
- Feriados manuais não são atualizados para o próximo ano
- QueryException em runtime

**Comportamento Esperado**:
Query deve usar string literal 'MANUAL' ou comparação com o enum completo.

**Correção Implementada**:
Corrigida sintaxe MANUAL para 'MANUAL'.

---

### BUG-006: Configuração Padrão Não Criada no Startup
**Status**: ❌ PENDENTE

**Localização**: `src/main/java/com/marcweb/MarcWebApplication.java`

**Descrição**:
A aplicação cria usuário admin padrão mas não cria configuração padrão da empresa. Quando o endpoint `/api/config-empresa` é acessado pela primeira vez, retorna 404.

**Impacto**:
- Aplicação não funciona imediatamente após setup
- Erro 404 em endpoint essencial
- Admin precisa criar configuração manualmente antes de usar sistema

**Comportamento Atual**:
- Sistema cria apenas usuário admin no startup
- Tabela `configs_empresa` fica vazia
- Primeiro acesso a `/api/config-empresa` falha

**Comportamento Esperado**:
Sistema deve criar uma configuração padrão com:
- Nome: "Empresa Exemplo LTDA"
- Coordenadas de referência (Feira de Santana)
- Raio: 100m
- GeolocAtiva: false

**Correção Necessária**:
Adicionar bloco no método `run()` para criar `ConfigEmpresa` padrão se não existir.

---

### BUG-007: SecurityConfig com RequestMatchers Incorretos
**Status**: ❌ PENDENTE

**Localização**: `src/main/java/com/marcweb/security/SecurityConfig.java`

**Descrição**:
Configuração de segurança tem mapeamentos para endpoints que não existem e URL incorreta para health check.

**Problemas Identificados**:
1. `/api/auth/health` deveria ser `/api/health`
2. `/api/registro-ponto/registrar` não existe (é `/api/ponto`)
3. `/api/registro-ponto/buscar` não existe (é `/api/ponto/me`)
4. Configuração desnecessariamente verbosa

**Impacto**:
- Endpoints fictícios configurados
- Health check pode não funcionar como esperado
- Confusão na manutenção do código
- Possível falha de segurança por configuração incorreta

**Comportamento Esperado**:
Configuração simples e clara:
- `/api/auth/login` → permitAll
- `/api/health` → permitAll
- `/error` → permitAll
- Tudo mais → authenticated

- Quantos já existiam no banco

### BUG-009: Endpoint de Sincronização Não Existe
**Status**: ❌ PENDENTE

**Localização**: 
- `src/main/java/com/marcweb/controller/FeriadoController.java`
- Documentação: `INFORMAÇÕES.txt`

**Descrição**:
O documento `INFORMAÇÕES.txt` especifica endpoint `POST /api/feriado/nacionais` mas o SDD menciona `POST /api/feriados/sync`. Além disso, o endpoint atual não retorna estatísticas.

**Impacto**:
- Inconsistência entre documentações
- Falta de feedback ao usuário
- Não segue padrão REST apropriado

**Comportamento Atual**:
Endpoint `POST /api/feriado/nacionais` existe mas:
- Retorna apenas 201 Created (sem corpo)
- Não informa quantos feriados foram adicionados
- Nome do endpoint não é intuitivo

**Comportamento Esperado**:
Endpoint deveria:
- Ter nome mais descritivo (`/sync` ou `/sincronizar`)
- Retornar JSON com estatísticas
- Status 200 OK com corpo de resposta
