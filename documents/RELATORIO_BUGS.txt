## 🔴 BUGS CRÍTICOS (Bloqueadores)

### BUG-001: NullPointerException em Primeiro Registro de Ponto - CORRIGIDO
**Arquivo:** `RegistroPontoService.java`  
**Método:** `validarRegistro(TipoRegistro tipoRegistro, Long idUsuario)`  
**Linha:** 31-33

**Descrição Detalhada:**  
Quando um usuário tenta registrar seu primeiro ponto (não há registros anteriores no banco), o método `repository.findLastTypeRegistration(idUsuario)` retorna NULL. O código não trata este cenário e tenta executar operações de comparação diretamente com o valor NULL, resultando em NullPointerException.

**Cenário de Reprodução:**
1. Criar um novo usuário no sistema
2. Fazer login com este usuário
3. Tentar registrar qualquer tipo de ponto
4. Sistema lança NullPointerException

**Impacto:**  
- Severidade: CRÍTICA
- Nenhum usuário novo consegue registrar seu primeiro ponto
- Aplicação falha completamente para novos funcionários
- Bloqueia a funcionalidade principal do sistema

**Comportamento Esperado:**  
O sistema deve detectar que é o primeiro registro e validar que o tipo seja ENTRADA. Se for outro tipo, deve retornar erro amigável informando que o primeiro registro deve ser uma entrada.

**Solução Requerida:**  
Adicionar verificação de NULL antes das comparações. Se ultimoTipoRegistro for NULL:
- Verificar se tipoRegistro é ENTRADA
- Se sim, permitir o registro (é válido)
- Se não, lançar exceção informando que primeiro registro deve ser ENTRADA
- Retornar do método (não executar validações subsequentes)

### BUG-002: Falta de Persistência de Feriados da BrasilAPI
**Arquivo:** `FeriadoController.java`  
**Método:** `buscarFeriados()`  
**Linha:** 22-25

**Descrição Detalhada:**  
O endpoint GET /api/feriado está implementado apenas para testar a conexão com a BrasilAPI. Os feriados são buscados da API externa mas nunca são salvos no banco de dados local. Segundo o SDD e o plano SCRUM (Sprint 6), deveria haver um endpoint /api/feriados/sync que busca E persiste os feriados.

**Cenário de Reprodução:**
1. Chamar GET /api/feriado
2. Sistema retorna lista de feriados
3. Consultar tabela 'feriados' no banco
4. Tabela está vazia

**Impacto:**  
- Severidade: CRÍTICA
- Cálculos de horas não consideram feriados (funcionalidade futura depende disso)
- Relatórios não marcarão dias como feriados
- Sistema não funciona conforme especificação do SDD

**Comportamento Esperado:**  
Deve existir um FeriadoService com método sincronizarFeriados() que:
- Busca feriados da BrasilAPI para o ano especificado
- Verifica quais já existem no banco (evitar duplicatas)
- Salva apenas os novos no banco com origem=API
- Retorna estatísticas da sincronização (quantos adicionados, quantos já existiam)

**Solução Requerida:**  
1. Criar FeriadoService completo
2. Implementar método sincronizarFeriados(int ano)
3. Adicionar verificação de duplicatas por data
4. Criar endpoint POST /api/feriados/sync que aceita ano como parâmetro
5. Proteger endpoint com @PreAuthorize("hasRole('ADMIN')")

### BUG-003: Ausência de Validação de Geolocalização Implementada
**Arquivos:** `RegistroPontoService.java`, `ConfigEmpresa.java`  
**Status:** Funcionalidade Parcialmente Implementada

**Descrição Detalhada:**  
O sistema possui campos para geolocalização (latitude, longitude, precisão) tanto em RegistroPonto quanto em ConfigEmpresa (latCentro, longCentro, raioGeoloc, geolocAtiva). No entanto, não há nenhuma validação implementada que:
- Verifique se a geolocalização está ativa (geolocAtiva)
- Calcule a distância entre o ponto registrado e o centro da empresa
- Rejeite registros fora do raio permitido
- Valide consentimento do usuário antes de coletar dados

**Cenário de Problema:**
1. Admin configura raio de 100 metros e ativa geolocalização
2. Funcionário registra ponto a 5km de distância
3. Sistema aceita o registro sem validação
4. Não há controle de presença física no local de trabalho

**Impacto:**  
- Severidade: CRÍTICA (para a proposta do sistema)
- Sistema não valida presença física
- Pode permitir fraudes (registrar de casa quando deveria estar no trabalho)
- Campos de geolocalização existem mas não são utilizados
- Violação potencial da LGPD (coleta sem validação de consentimento)

**Comportamento Esperado:**  
Quando geolocAtiva=true em ConfigEmpresa:
- Verificar consentGeoloc do usuário (se false, rejeitar ou avisar)
- Calcular distância usando fórmula de Haversine
- Se distância > raioGeoloc, lançar exceção específica
- Registrar no log de auditoria se houve tentativa fora do raio
- Se geolocAtiva=false, aceitar registros sem coordenadas

**Solução Requerida:**  
1. Criar método calcularDistanciaHaversine() no RegistroPontoService
2. Adicionar validação no método registrarPonto() que:
   - Busca ConfigEmpresa
   - Se geolocAtiva=true, valida coordenadas obrigatórias
   - Calcula distância
   - Compara com raio permitido
   - Lança RegistroPontoForaDoRaioException se inválido
3. Criar nova exceção customizada: RegistroPontoForaDoRaioException
4. Adicionar handler no ControllerException

### BUG-005: Ausência de Índice em Query Frequente
**Arquivo:** `RegistroPontoRepository.java`  
**Query:** `findLastTypeRegistration()`  
**Linha:** 24-27

**Descrição Detalhada:**  
A query nativa que busca o último tipo de registro usa ORDER BY timestamp DESC LIMIT 1. Esta query será executada em TODA tentativa de registro de ponto (uso muito frequente). O índice existente é composto (user_id, timestamp), mas a query pode não estar otimizada para este caso específico.

**Cenário de Problema:**
1. Empresa com 50 funcionários
2. Cada funcionário registra 4 pontos por dia
3. Total: 200 registros/dia
4. Após 1 ano: 73.000 registros
5. Query sem índice adequado pode demorar muito

**Impacto:**  
- Severidade: ALTA (performance)
- Degradação de performance ao longo do tempo
- Cada registro de ponto fica mais lento conforme tabela cresce
- Máquinas com 4GB RAM podem sofrer mais

**Comportamento Esperado:**  
Query deve usar índice eficiente e executar em milissegundos mesmo com milhões de registros.

**Solução Requerida:**  
1. Analisar plano de execução (EXPLAIN ANALYZE) da query
2. Verificar se o índice idx_registro_user_data está sendo usado
3. Considerar criar índice específico: CREATE INDEX idx_user_timestamp_desc ON registros_ponto (user_id, timestamp DESC)
4. Adicionar migration do Flyway para criar índice
5. Testar performance com dados de volume (inserir 100k registros de teste)

### BUG-006: Falta Tratamento de Erro em Chamada Externa
**Arquivo:** `BrasilApiService.java`  
**Método:** `buscarFeriados()`  
**Linha:** 13-18

**Descrição Detalhada:**  
O método buscarFeriados() faz chamada HTTP para API externa usando WebClient.block(). Não há tratamento de erro para:
- API indisponível (timeout, erro 5xx)
- Resposta inválida (JSON malformado)
- Ano inválido retornando 404
- Limite de requisições excedido (rate limit)

**Cenário de Problema:**
1. Chamar sincronização de feriados
2. BrasilAPI está fora do ar
3. Sistema trava esperando resposta
4. Lança WebClientException não tratada
5. Usuário vê erro genérico 500

**Impacto:**  
- Severidade: ALTA (confiabilidade)
- Sistema depende de serviço externo sem fallback
- Erros não são informativos
- Pode causar timeouts longos bloqueando threads

**Comportamento Esperado:**  
- Timeouts configurados (ex: 5 segundos)
- Retry automático (ex: 3 tentativas)
- Mensagens de erro claras
- Fallback: se API falhar, retornar lista vazia e logar erro
- Não bloquear funcionamento de outras partes do sistema

**Solução Requerida:**  
1. Configurar timeouts no WebClient
2. Adicionar try-catch específicos para WebClientException
3. Implementar retry logic com backoff exponencial
4. Criar custom exception: BrasilApiFalhaException
5. Logar erros com detalhes para diagnóstico
6. Retornar Optional ou Result object ao invés de lançar exceção

### BUG-007: Falta Validação de Sequência Correta Completa
**Arquivo:** `RegistroPontoService.java`  
**Método:** `validarRegistro()`  
**Linha:** 36-48

**Descrição Detalhada:**  
A validação de sequência de registros tem problemas lógicos:
1. Não valida se o usuário já registrou SAÍDA no mesmo dia (permitiria múltiplos ciclos no mesmo dia)
2. Não valida horário mínimo entre registros (poderia registrar ENTRADA e SAÍDA no mesmo segundo)
3. Não valida se é o mesmo dia (ENTRADA às 23:59 e SAÍDA às 00:01 do dia seguinte)
4. Permite apenas 1 período de descanso por dia (CLT permite múltiplos se jornada > 6h)

**Cenário de Problema:**
1. Funcionário registra: ENTRADA 08:00
2. Registra INICIO_DESCANSO 08:01
3. Registra FIM_DESCANSO 08:02
4. Registra SAÍDA 08:03
5. Registra ENTRADA 08:04 (começou novo ciclo)
6. Sistema permite, mas não deveria (múltiplos ciclos no mesmo dia sem justificativa)

**Impacto:**  
- Severidade: ALTA (regra de negócio)
- Permite comportamentos inválidos conforme CLT
- Cálculos de horas podem ficar incorretos
- Relatórios ficam inconsistentes
- Possibilita fraudes

**Comportamento Esperado:**  
- Validar que é o primeiro ciclo do dia (ou exigir justificativa para novo ciclo)
- Validar intervalo mínimo entre registros (ex: 1 minuto)
- Validar que todos os registros do ciclo são do mesmo dia
- Permitir múltiplos períodos de descanso se configurado

**Solução Requerida:**  
1. Buscar todos os registros do dia atual antes de validar
2. Verificar se já existe ciclo completo (ENTRADA→SAÍDA)
3. Se sim, exigir campo "justificativa" no DTO
4. Adicionar validação de intervalo mínimo (configurável em ConfigEmpresa)
5. Validar que timestamp atual está no mesmo dia do último registro incompleto
6. Criar lógica para permitir múltiplos descansos (futura melhoria)

## 🟡 BUGS DE MÉDIA PRIORIDADE

### BUG-008: Ausência de Paginação em Endpoints de Listagem
**Arquivos:** `RegistroPontoController.java`, todos os repositories  
**Métodos:** `meusPontos()`, futuros endpoints de listagem

**Descrição:**  
Nenhum endpoint de listagem implementa paginação. O endpoint /api/ponto/me retorna TODOS os registros do período solicitado. Para um funcionário com 1 ano de trabalho (1000+ registros), isso pode causar:
- Resposta HTTP muito grande
- Alto uso de memória
- Lentidão no frontend
- Possível timeout

**Impacto:**  
- Severidade: MÉDIA (escalabilidade)
- Problema não aparece no início, mas piora com tempo
- Máquinas com 4GB RAM sofrerão primeiro

**Solução Requerida:**  
1. Adicionar suporte a Pageable do Spring Data
2. Retornar Page<> ao invés de List<>
3. Aceitar parâmetros: page, size, sort
4. Implementar em TODOS os endpoints de listagem futuros
5. Documentar nos DTOs de resposta (totalPages, totalElements, etc)

### BUG-009: Senha do Admin em Texto Plano no Código
**Arquivo:** `MarcWebApplication.java`  
**Linha:** 29

**Descrição:**  
A senha padrão do admin ("admin123") está hardcoded no código-fonte. Isso é uma falha de segurança porque:
- Qualquer pessoa com acesso ao código conhece a senha
- Se o código vazar (ex: GitHub público), sistema fica vulnerável
- Mesmo em repo privado, é má prática

**Impacto:**  
- Severidade: MÉDIA (segurança)
- Senha previsível e conhecida
- Violação de boas práticas de segurança
- Risco aumenta se código for open-source

**Solução Requerida:**  
1. Mover senha padrão para variável de ambiente (ADMIN_DEFAULT_PASSWORD)
2. Ou gerar senha aleatória no primeiro boot e logar no console
3. Forçar troca de senha no primeiro login do admin
4. Adicionar no README instruções de segurança
5. Considerar remover criação automática e exigir setup manual em produção

### BUG-010: Falta Logs de Auditoria Automáticos
**Status:** Funcionalidade Não Implementada (Sprint 8)  
**Impacto:** Todos os controllers

**Descrição:**  
Segundo o SDD, todas as ações críticas devem ser registradas em logs_auditoria. Atualmente:
- Login não é auditado
- Criação/edição/exclusão de usuários não é auditada
- Registro de ponto não é auditado
- Alterações em ConfigEmpresa não são auditadas

**Impacto:**  
- Severidade: MÉDIA (compliance/segurança)
- Impossível rastrear ações no sistema
- Dificulta investigação de problemas
- Não atende requisitos de auditoria empresarial
- LGPD exige logs de acesso a dados pessoais

**Solução Requerida (Sprint 8, mas planejar agora):**  
1. Criar Aspect com @Around em métodos dos services
2. Capturar usuário do contexto de segurança
3. Salvar em LogAuditoria com: ação, timestamp, userId, detalhes, status
4. Categorizar por tipo: PONTO, ADMIN, AUDITORIA, SISTEMA
5. Implementar de forma não intrusiva (sem poluir código dos services)

## 🟢 BUGS DE BAIXA PRIORIDADE

### BUG-011: Falta Validação de Formato de IP
**Arquivo:** `RegistroPontoService.java`  
**Método:** `getIpUser()`  
**Linha:** 63-68

**Descrição:**  
O método extrai o IP do header X-Forwarded-For ou RemoteAddr, mas não valida se o formato é válido (IPv4 ou IPv6). Se o header for manipulado, pode salvar string inválida no banco.

**Impacto:**  
- Severidade: BAIXA (qualidade de dados)
- IP pode ser inválido no banco
- Não afeta funcionamento do sistema
- Apenas reduz qualidade de auditoria

**Solução Requerida:**  
1. Adicionar regex para validar formato IPv4/IPv6
2. Se inválido, salvar como "INVALID" ou NULL
3. Logar warning quando IP for inválido
4. Considerar usar biblioteca Apache Commons Validator

## 🔍 PROBLEMAS DE DESIGN E ARQUITETURA

### DESIGN-001: Falta Interface de Service
**Descrição:** Os services não implementam interfaces, dificultando mock em testes e violando princípio de Inversão de Dependência (SOLID).

**Recomendação:** Criar interfaces IUserService, IRegistroPontoService, etc.

### DESIGN-002: Ausência de DTOs de Response Padronizados
**Descrição:** Alguns endpoints retornam entidades JPA diretamente, outros retornam DTOs. Falta padronização.

**Recomendação:** Sempre retornar DTOs, nunca entidades. Criar ResponseDTO para cada endpoint.

### DESIGN-003: Falta Tratamento Global de Exceções
**Descrição:** ControllerException existe mas não trata exceções genéricas (NullPointerException, IllegalArgumentException, etc).

**Recomendação:** Adicionar @ExceptionHandler para Exception.class com log e resposta genérica.

## 🛡️ POTENCIAIS VULNERABILIDADES DE SEGURANÇA

### SEC-001: CORS Aberto em Desenvolvimento
**Arquivo:** `SecurityConfig.java`  
**Linha:** 50 - `setAllowedOriginPatterns(List.of("*"))`

**Descrição:** Permite requisições de qualquer origem. Em produção, isso deve ser restrito.

**Recomendação:** Criar perfil prod com origens específicas.

### SEC-002: Ausência de Rate Limiting
**Descrição:** Endpoint /api/auth/login não tem proteção contra brute force.

**Recomendação:** Implementar rate limiting (ex: 5 tentativas por minuto por IP).

### SEC-003: Token JWT Sem Refresh Token
**Descrição:** Token expira em 8h mas não há mecanismo de refresh, usuário precisa fazer login novamente.

**Recomendação:** Implementar refresh token para melhor UX e segurança.
